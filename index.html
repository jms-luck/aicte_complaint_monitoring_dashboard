AICTE Integrated Institution
Complaint Monitoring & Status Dashboard

A centralised platform for managing institution-related complaints and regulatory cases across AICTE's Bureaus and Cells — with cross-bureau overlap detection, SLA monitoring, and role-based access control.

React 18 + Vite + TypeScript FastAPI + Python 3.12 PostgreSQL 16 JWT Auth RapidFuzz Overlap Detection APScheduler Docker Compose Azure Blob Storage

📋 Project Overview

The platform centralises institution-related complaints and regulatory cases across AICTE's internal departments — the Regulation Bureau (RB), Public Grievance Redressal Cell (PGRC), regional offices, and other Bureaus/Cells.

Primary goals: prevent duplicated efforts, detect potentially overlapping cases, improve interdepartmental coordination, track case movement, monitor deadlines, and give management consolidated reports.

Unified Complaint Intake

Accept complaints from portal, email, letter, RTI, and court orders. Centralise all sources into a single tracking system.

Cross-Bureau Overlap Detection

Detect potentially related cases across departments using exact ID matching, fuzzy name matching (RapidFuzz), and optional semantic similarity (Sentence Transformers).

SLA & Deadline Monitoring

Configurable SLA rules per category, priority, and bureau. Background scheduler triggers overdue alerts, approaching-deadline reminders, and escalation notifications.

Role-Based Access Control

Six user roles with backend-enforced permissions. Every protected endpoint checks authorization — hiding a button is not sufficient.

Real-Time Dashboard & Analytics

KPI cards, trend charts, workload distribution, ageing analysis, and overlap alert tracking — all driven from live database queries.

CSV / JSON Reports

Export institution-wise history, ageing analysis, bureau workload, overlap reports, and more — with date-range and bureau filters.

  • Full-text search and filtering

Complaint & Case Management

  • Unique complaint and case IDs
  • Status lifecycle: Received → Disposed → Closed
  • Assign, reassign, transfer between bureaus
  • Add remarks, actions, and documents
  • Configurable status transitions (backend validated)
  • Case reopening with authorization
  • Search, sort, filter, paginate
Module D

Institution-Centric Dashboard

  • KPI cards: total, active, pending, overdue, overlapping
  • Cases by status and Bureau/Cell charts
  • Monthly intake and disposal trends
  • Pending-case ageing analysis
  • Regional workload distribution
  • Unified institution table with bureau breakdown
  • All metrics from live database queries
Module E

Cross-Bureau Overlap Detection

  • Stage 1: Exact AICTE Permanent ID / case ref matching
  • Stage 2: RapidFuzz institution-name fuzzy matching
  • Stage 3: Complaint text + optional semantic similarity
  • Stage 4: Overlap classification (same/possible/related/false)
  • Alert lifecycle with review workflow
  • No automatic case merging — human review required
  • Deduplication of active alerts for same candidate pair
Module F

Related-Case Coordination Workspace

  • Unified view of linked cases across departments
  • Institution identity and case reference side-by-side
  • Responsible bureau, assigned officer, status per case
  • Coordination notes and interdepartmental review requests
  • All coordination decisions recorded in audit trail
  • Original case records remain independent
Module G

Workflow & Audit Trail

  • Chronological history for all important operations
  • Entity, action, actor, timestamp per entry
  • Before/after values for status changes
  • Server-generated timestamps (immutable by users)
  • Action history stored separately from case state
  • Database transactions for case + audit event atomicity
Module H

SLA Monitoring & Notifications

  • Configurable SLA rules (category, priority, bureau)
  • Pending reminders, deadline alerts, overdue alerts
  • Escalation and unreviewed overlap reminders
  • Assignment notifications
  • Idempotent scheduled processing (no duplicate notifications)
  • In-app notification center with unread counts
  • Optional SMTP email delivery

Search & Filtering

  • Institution name, AICTE ID, complaint/case ID

  • Assigned officer, overlap review status, date range

  • Backend-powered with pagination + DB indexes

Module J

Reports & Analytics

✅ End-to-End Acceptance Scenario

The project is not complete until this full workflow succeeds:

  1. 1
    Login as admin@aicte.gov.in and create an institution with a verified AICTE Permanent ID.
  2. 2
    As PGRC Officer, register a fee-refund complaint for that institution. Create a case and mark it Under Process.
  3. 3
    As RB Officer, register a separate complaint for the same institution from a different bureau.
  4. 4
    The system detects the common institution and generates a "Potential Overlapping Cases — Coordination Required" alert in the overlap review center.
  5. 5
    An authorized official compares the two cases side by side and records a review decision (confirmed_related).
  6. 6
    The official links the cases as related — both cases retain their independent statuses and histories.
  7. 7
    The dashboard updates case counts and overlap statistics from the database.
  8. 8
    An officer records an action — the system appends an audit-history entry.
  9. 9
    A case approaching its configured deadline generates an appropriate SLA notification.
  10. 10
    An unauthorized user is prevented from accessing restricted case details and documents.
  11. 11
    An officer exports a filtered CSV report — the export reflects only the records matching the applied filters.
⚠️ Two complaints about the same institution must never be automatically treated as duplicates. Cases remain independent unless an authorized workflow explicitly links them.

🌐 Production Deployment (Azure)

1. Database

Provision Azure Database for PostgreSQL Flexible Server. Enable automated daily backups with 7-day retention minimum.

2. App Service

Create Azure App Service (Python 3.12, B2 or higher). Configure environment variables via App Service Configuration.

3. Document Storage

Create Azure Blob Storage container. Set USE_LOCAL_STORAGE=false and provide the connection string.

4. Secret Management

Store SECRET_KEY, DB credentials, and SMTP passwords in Azure Key Vault. Reference them as App Service env variables.

Post-deploy commands
# Run database migrations alembic upgrade head # Seed initial data (development/staging only) python -m app.db.seed # Required environment variables in production DATABASE_URL=postgresql://... # Azure PostgreSQL connection string SECRET_KEY=<64-char random string> AZURE_STORAGE_CONNECTION_STRING=DefaultEndpointsProtocol=https;... ENVIRONMENT=production USE_LOCAL_STORAGE=false
🔒 In production, terminate TLS at the load balancer or App Service level. Never run FastAPI directly on port 443. Use --workers 1 with gunicorn if using APScheduler (in-process), or migrate to Celery for multi-worker deployments.

⚠️ Known Limitations

  • 1
    Semantic matching disabled by default. The Sentence Transformers model is not downloaded automatically. To enable: set use_semantic=True in MatchConfig and pre-download the model in production.
  • 2
    Email notifications require SMTP configuration. Leave SMTP_HOST empty to disable email sending. Notifications are still created in the database and visible in the in-app center.
  • 3
    Azure Blob Storage requires an Azure account. Set USE_LOCAL_STORAGE=false and provide AZURE_STORAGE_CONNECTION_STRING. Local filesystem storage is used by default for development.
  • 4
    APScheduler runs in-process. In a multi-worker deployment (gunicorn), the background scheduler runs in every worker. Use --workers 1 or migrate to an external task queue (Celery + Redis) for production.
